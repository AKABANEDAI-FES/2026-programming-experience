# システムアーキテクチャ・データフロー

## 1. コンポーネント

このシステムは主に以下の4つの要素で構成されます。

- **参加者画面（フロントエンド：React）**: 子どもがお絵かきやプログラミングをする端末。
- **APIサーバー（バックエンド：Cloudflare Workers + Hono）**: データを受け取り、各所へ振り分ける関所。
- **ストレージ（Cloudflare R2）**: 画像データ（SVG等）を安全に保存するクラウドの保管庫。
- **大画面モニター（展示用フロントエンド）**: 会場でみんなの描いた絵が泳ぐメイン画面。

## 2. 画面遷移とデータの流れ（フロントエンド側）

参加者がタブレットを操作するフローは「完全一方通行」で設計されています。

1. **【画面①】ホーム画面**:
   - アプリの入り口。「自由にお絵かき」または「イニャーの塗り絵」のどちらかのボタンを押して体験を開始します。
2. **【画面②】お絵かき・塗り絵画面**:
   - 参加者は画面①で選んだモード（白紙または下絵あり）でキャラクターを作成します。
   - 完成した絵はSVG等のデータとして保持され、「次へ」を押すと画面③へ進みます（戻る操作不可）。
3. **【画面③】プログラミング画面（Blockly）**:
   - Blocklyを使用してキャラクターの動きをブロックで組み立てます。
   - 「放流する」ボタンを押すと、画面②のPNG画像データと画面③のコマンド配列が1つのセットにまとめられます。コマンドは空でも送信できます。
4. **【画面④】完了画面**:
   - 成功メッセージを表示後、一定時間で画面①に戻ります。

## 3. システム間のデータフロー（バックエンド側）

「放流する」ボタンが押されてから、大画面に絵が表示されるまでの流れは以下の通りです。

1. **参加者画面**が、絵のデータとプログラム（JSON）を冪等性キー付きで**APIサーバー**にPOST送信します。同じ送信の再確認には同じキーを使います。
2. **APIサーバー**は、受け取った画像データを**ストレージ（R2）**に保存します。
3. R2への保存後、**APIサーバー**はWebSocket / Durable Objectsを使って、接続中の**大画面モニター**へ「新しい絵が追加されたよ！」という通知をプッシュ送信します。通知はベストエフォートで、APIの成功条件はR2への保存です。
4. 通知を受け取った**大画面モニター**が、**ストレージ**からその絵とプログラムを読み込み、画面の海へと泳がせます。

## 4. リアルタイム通信を採用する理由

大画面モニター側から「新しい絵は来ましたか？」と一定時間ごとに何度も確認しに行く方式（ポーリング）ではなく、サーバーからのプッシュ通知（リアルタイム通信）を採用した理由は以下の通りです。

- **無駄な通信（リクエスト）の削減**: 参加者が誰も描いていない時間帯でも、大画面が問い合わせを続けるのは非効率なため。
- **サーバー負荷の軽減**: 大量のリクエストによるCloudflareの利用制限や、システム全体のパフォーマンス低下（遅延など）を防ぎ、安定した展示運営を行うため。
